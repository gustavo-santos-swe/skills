What this repo is Not a conventional application. It is process documentation that executes: each skills/<area>/<name>/SKILL.md is a playbook an LLM agent loads and follows. A handful of supporting scripts (a local visual-companion web server, upstream sync tooling, code-analysis helpers) make some skills interactive or automatable.

#Architecture

The delivery model is intentionally simple — a public GitHub repo acting as the source of truth, with an MCP gateway in front:

┌──────────────────────────┐      push to main      ┌─────────────────────────────┐
│  github.com/             │ ─────────────────────▶ │  mcp.skillsovermcp.com      │
│  gustavo-santos-swe/     │                        │  /mcp/gustavo-santos-swe/   │
│  skills  (public)        │                        │  skills  (streamable-http)  │
└──────────────────────────┘                        └──────────────┬──────────────┘
                                                                   │ tools = skills
                                                    ┌──────────────▼──────────────┐
                                                    │  MCP clients                │
                                                    │  Cursor · Claude Code ·     │
                                                    │  Codex · any MCP client     │
                                                    └─────────────────────────────┘
  • Distribution: each skill is exposed as an MCP tool. Agents read the description frontmatter to decide when to load a skill, then read the full body and follow it.
  • Versioning: git is the only version control. There are no releases — main is production.
  • Provenance: most skills are synced from upstream repos (obra/superpowers, anthropics/skills, mattpocock/skills, etc.) and carry metadata.upstream frontmatter with repo, path, pinned commit SHA, and sync date. Custom skills (ship-feature) are marked as such.

#Workflow pipeline

The skills compose into one canonical development flow:

brainstorming→ writing-plans→ executing-plans→ TDD / frontend-design / systematic-debugging→ verification-before-completion→ code-simplification→ requesting-code-review→ ship-feature

When multiple skills could apply, priority is: process skills (how to approach) → implementation skills (execution) → completion skills (verification, shipping). Skills are typed as rigid (TDD, debugging, verification — follow exactly) or flexible (brainstorming, planning — adapt principles).

#Coding conventions (how this codebase works)

Extracted from the skills themselves — these are the house rules any agent or contributor is expected to follow:

Process discipline

  • Skill check first. If there is even a 1% chance a skill applies, read it and follow it — before clarifying questions, before exploring code. User instructions always outrank skills.
  • TDD iron law. No production code without a failing test first. Code written before the test gets deleted, not adapted. The same law applies to skill authoring: no skill without a failed baseline scenario first.
  • Root-cause before fix. Systematic debugging forbids symptom-patching; trace to the cause, then fix with a test.
  • Evidence before "done". Verification-before-completion requires running the actual commands and reading the output before claiming success.

Git & shipping

  • Conventional commits, one-liner: <type>(<scope>): imperative lowercase description.
  • Feature branches only — never commit to main, never local merge, never gh pr merge, never force-push. Integration happens exclusively via PR.
  • No --no-verify unless explicitly requested. Tests must pass before commit.
  • PRs carry a Summary + Test plan checklist (template in ship-feature/references/).

Skill authoring

  • Frontmatter description states only when to trigger ("Use when…"), never the workflow — summarizing the process makes agents skip the body.
  • Token economy: frequently-loaded skills < 200 words; others < 500 lines; heavy reference goes in references/; never @-force-load other files.
  • Verb-first kebab-case names (writing-plans, not plan-writing); one excellent code example beats five mediocre ones.
  • Discipline skills must be bulletproofed: rationalization tables, red-flag lists, explicit loophole closures — tested under pressure with subagents.
  • Upstream provenance is mandatory metadata: repo, path, commit (pinned SHA), synced_at; adapted skills add a note, which blocks automatic sync unless --force.

Script style (observed)

  • Bash: set -euo pipefail, array-based arg building to avoid glob expansion, usage functions, stderr for diagnostics.
  • Python: stdlib-only, from __future__ import annotations, dataclasses, type hints, argparse with --dry-run flags.
  • Node: zero-dependency (hand-rolled RFC 6455 WebSocket rather than pulling in ws), explicit lifecycle management (owner PID + idle timeout).

#Deep analysis — executable surface

Although this is mostly a documentation repo, three clusters of code actually run on the user's machine and define the attack surface:

1. Brainstorm visual companion (workflow/brainstorming/scripts/)

A zero-dependency Node HTTP + WebSocket server (server.cjs, ~350 lines). The agent writes HTML "screens" into a session directory; the server watches the directory, serves the newest screen at /, injects helper.js for click capture, and streams user choices back over WebSocket. Lifecycle is well-engineered: binds 127.0.0.1 by default, random high port, 30-minute idle timeout, exits when the owning agent process dies.

2. Upstream sync tooling (meta/sync-upstream-skills/scripts/)

check-upstream.py compares each skill's pinned commit against the latest upstream commit via the GitHub API (optional GITHUB_TOKEN from env, never hardcoded). sync-skill.py downloads all files of a skill from raw.githubusercontent.com at the latest commit and overwrites the local copy, then updates frontmatter. Skills with an adaptation note refuse to sync without --force.

3. Analysis helpers (engineering/*/scripts/)

ripgrep + jq pipelines for function extraction and duplicate reporting; a test-pollution bisection script; the mcp-builder eval harness (Anthropic upstream, requires ANTHROPIC_API_KEY via env).

#Threat model

For an agent-skills repo, the most important risks are not classic web-app bugs — they are trust-chain risks. Three trust boundaries matter:

BoundaryRiskCurrent posture
Upstream repos → this repo A compromised upstream (obra/superpowers, etc.) injects malicious instructions that sync-skill.py copies in verbatim — a prompt-injection supply chain. Commits are pinned in metadata, but sync always pulls latest; no diff review is enforced by tooling. Mitigated by the documented manual-review workflow.
This repo → MCP consumers Push to main = instant deployment to every connected agent. Anyone who can write to the repo can steer agent behavior on all consumer machines. The using-superpowers skill instructs agents that skill use is "not negotiable", amplifying whatever the skills say. Single-owner repo, single contributor. The instruction-priority section explicitly caps skills below user instructions — a good guardrail.
Agent → local machine (brainstorm server) The server intentionally renders agent-generated HTML in the user's browser and accepts WebSocket input. Exposure depends on bind host and the predictability of the session directory. Localhost-only by default, random port, idle timeout. Risk grows with --host 0.0.0.0 (no auth) and the /tmp default on shared machines.
Secret scan result: clean. A repo-wide scan for keys, tokens, passwords, and bearer strings found only documentation examples (ghp_xxx, token123) and proper env-var usage (GITHUB_TOKEN, ANTHROPIC_API_KEY). .gitignore covers .env / .env.local, and the README explicitly states the repo is public and must never hold secrets.

#OWASP Top 10 (2021) assessment

Mapped against the actual executable surface and delivery model. Severities are contextual to a personal dev-tool repo.

CategoryRiskAssessment
A01 Broken Access Control MEDIUM The brainstorm server has no authentication on HTTP or WebSocket. Safe while bound to 127.0.0.1 (default), but start-server.sh --host 0.0.0.0 — documented for containers/remote — exposes an unauthenticated screen-viewer + event channel to the network. Path traversal on /files/ is correctly blocked via path.basename().
A02 Cryptographic Failures LOW No secrets stored or transmitted by the repo itself. WebSocket runs over plain ws:// — acceptable for localhost; becomes relevant only in the 0.0.0.0 scenario. Tokens are consumed exclusively from environment variables.
A03 Injection MEDIUM Serving agent-generated HTML is the product's design, so XSS-by-design is accepted. Two real issues: (1) helper.js builds indicator.innerHTML from DOM-derived label text — a screen containing user-influenced content could inject markup; (2) find-polluter.sh iterates unquoted $TEST_FILES (word-splitting on paths with spaces) and interpolates arguments into suggested commands. The jq/ripgrep pipelines correctly use argument arrays.
A04 Insecure Design LOW Design is deliberately minimal and mostly sound: localhost default, random ports, idle timeout, owner-PID lifecycle, masked-frame enforcement per RFC 6455, commit pinning for upstream provenance. The accepted-by-design risk is rendering agent HTML in the browser, which the skill discloses to the user before enabling.
A05 Security Misconfiguration MEDIUM Default session dir /tmp/brainstorm-* is world-readable/writable territory on shared Unix machines — another local user could drop an .html file into the content dir and have it rendered in the victim's browser (the watcher serves the newest file). The --host 0.0.0.0 flag carries no warning about the lack of auth.
A06 Vulnerable & Outdated Components LOW Outstanding posture: the server hand-implements WebSocket to keep zero npm dependencies; Python scripts are stdlib-only. The only third-party deps (mcp, anthropic) live in the mcp-builder tooling and are unpinned in requirements.txt — minor.
A07 Identification & Authentication Failures INFO No auth exists anywhere by design: the MCP endpoint is intentionally public (documented), and the local server trusts anything that can reach its socket. Consolidated with A01; no separate failure beyond that.
A08 Software & Data Integrity Failures HIGH The most significant category for this project. (1) sync-skill.py downloads upstream files and writes them verbatim with no checksum/signature and no enforced diff review — a compromised upstream becomes instructions agents will execute. (2) Push-to-main is instant, review-gate-free deployment to all MCP consumers. (3) raw.githubusercontent.com fetches use the latest commit rather than the reviewed, pinned SHA.
A09 Security Logging & Monitoring Failures LOW Proportional to the tool: the server logs structured JSON lifecycle and user events to stdout/log file; sync scripts report per-skill status. No sensitive data is logged. No monitoring of who consumes the MCP endpoint — acceptable for a personal repo.
A10 Server-Side Request Forgery LOW Outbound requests are pinned to api.github.com and raw.githubusercontent.com. However, repo and path are interpolated from SKILL.md frontmatter into URLs — path is percent-encoded but repo is not validated against an owner/name pattern, allowing URL-shape manipulation within github.com. Low impact, easy fix.

#Detailed findings

HIGHF-01 · A08

Unverified upstream sync = prompt-injection supply chain

sync-skill.py resolves the latest upstream commit, downloads every file under the skill path, and overwrites local content byte-for-byte. Skills are instructions that agents on every connected machine will obey (reinforced by using-superpowers' "not negotiable" framing). A compromised or hostile upstream commit flows: upstream → local repo → push → MCP → all agents.

Recommendation — always run sync on a branch, review the full diff before merging (make this a hard rule in the skill), and consider verifying downloaded content against the GitHub tree API blob SHAs for the pinned commit.

MEDIUMF-02 · A01/A05

Unauthenticated server on non-loopback binds

start-server.sh --host 0.0.0.0 is offered for containers/remote sessions with no authentication and no warning. Anyone on the network can view brainstorm screens (potentially containing project/spec details) and inject WebSocket choice events that the agent will treat as the user's decisions.

Recommendation — generate a random token at startup, require it as a URL query parameter, and echo a warning whenever the bind host is not loopback.

MEDIUMF-03 · A05

Predictable world-writable session directory

Default sessions live in /tmp/brainstorm-$$-<epoch>. On multi-user systems, /tmp is shared; the server renders whichever .html file in the content dir is newest, so another local user who guesses/lists the path can plant a screen that the victim's browser renders with the WebSocket helper attached.

Recommendation — create the session dir with mkdir -m 700, or default to a user-owned location (e.g. $XDG_RUNTIME_DIR or ~/.cache/brainstorm).

LOWF-04 · A03

innerHTML interpolation in helper.js

The selection indicator does indicator.innerHTML = '<span>' + label + '…' where label is text content scraped from the rendered screen. Since screens may embed user- or document-derived strings, this is a small second-order injection vector inside an already-trusted page.

Recommendation — build the indicator with textContent + createElement instead of string-concatenated HTML.

LOWF-05 · A03

Shell quoting gaps in find-polluter.sh

The loop for TEST_FILE in $TEST_FILES word-splits on whitespace, breaking (or mis-targeting) on paths with spaces; $POLLUTION_CHECK flows into ls -la and suggested commands unquoted. Exploitability is negligible (developer runs it on their own repo) but it contradicts the repo's own bash standards seen in extract-functions.sh.

Recommendation — use find … -print0 | while IFS= read -r -d '' and quote all expansions.

LOWF-06 · A06/A10

Hardening nits

(1) mcp-builder/scripts/requirements.txt pins no versions. (2) sync-skill.py does not validate repo against ^[\w.-]+/[\w.-]+$ before URL interpolation. (3) The DoS-hardening of the hand-rolled WebSocket decoder is minimal (no max payload size) — irrelevant on loopback, relevant if F-02 is ever exercised.

#Recommendations & strengths

What is already done well

  • Zero-dependency philosophy — no npm packages to audit, stdlib-only Python; the supply-chain surface for code is essentially nil.
  • Secret hygiene — clean scan, env-var-only tokens, .env gitignored, public-repo warning in the README.
  • Provenance metadata — every synced skill pins repo, path, commit SHA, and date; adapted skills are protected from blind overwrite by the note + --force gate.
  • Lifecycle engineering — owner-PID monitoring, idle timeout, localhost default, random ports, traversal-safe file serving.
  • Instruction priority guardrail — skills explicitly rank below user instructions, limiting the blast radius of a malicious skill.
  • Process discipline — never-merge-to-main, conventional commits, TDD-for-docs with adversarial subagent testing.

Priority actions

  1. Now: add a mandatory "sync on a branch + review full diff" rule to sync-upstream-skills (F-01).
  2. Soon: token-gate the brainstorm server for non-loopback binds, and warn loudly on 0.0.0.0 (F-02).
  3. Soon: chmod 700 session directories / move default out of /tmp (F-03).
  4. Opportunistic: F-04 → F-06 — small, mechanical fixes next time those files are touched.
